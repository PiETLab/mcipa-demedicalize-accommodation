# ActionForge remote implementation verification — 2026-10-06

## 1.1 Verification framing and release identification

### 1.1.1 Purpose and verification boundary

This record verifies the **remote ActionForge system**. It does not verify whether a local checkout can be built through a local Quartz installation, including whether the source tree builds successfully.

The system under examination consists of:

1. the target commit on GitHub `main`;
2. the GitHub Actions workflow that builds and deploys the site;
3. the deployed GitHub Pages site and public feedback interface;
4. the deployed Cloudflare Worker feedback endpoint; and
5. the structured GitHub issue record created by an authorized controlled submission.

Local commands are used only to identify the target commit and prepare changes. A successful local build or test suite is supplementary evidence; it does not verify the deployed Worker, GitHub Actions run, public interface, or service-account issue creation.

### 1.1.3 Planned release identification

This verification record is intended for inclusion in a later repository snapshot. Thus, it does not embed that snapshot’s fixed commit SHA: inserting such a SHA after committing the record would require a further commit and therefore produce a different SHA.

**Release mechanism.** After this record is finalized, a release maintainer will commit it to `main`, then create and push the planned annotated tag on that commit. When created, the tag will become the authoritative identifier for the release snapshot containing this verification record and any other materials included in that commit.

**Table 1. Planned release identification**

| Release field    | Planned value                   | Becomes established when                                                 |
| ---------------- | ------------------------------- | ------------------------------------------------------------------------ |
| Annotated tag    | `actionforge-pilot-follow-up-1` | A release maintainer creates and pushes an annotated tag with this name. |
| Branch condition | `main`                          | The tagged commit is confirmed as reachable from `main`.                 |

After tagging, the tag’s target commit SHA can be resolved with:

```sh
TAG_NAME='<the Annotated tag name from Table 1>'
git rev-parse "${TAG_NAME}^{commit}"
```

### 1.2.5 Verification conclusions

#### 1.2.5.1 Verified remote functionality

- GitHub `main` at the baseline commit was successfully deployed by the recorded GitHub Actions run.
- The GitHub Pages prototype and its key public routes were reachable on the `Verification date`; the deployed homepage included build assets bearing the baseline-commit prefix.
- The deployed public-feedback interface and Cloudflare Worker endpoint were available. Historical production evidence in [Issue #64](https://github.com/PiETLab/mcipa-demedicalize-accommodation/issues/64) confirms service-account creation of a public passage-feedback issue with source/object labels and preserved contextual provenance.
- Public-data terms were available before submission through the linked Public Feedback Policy.

#### 1.2.5.2 Not verified

- Failure recovery has not been observed end to end: this record does not establish whether a failed submission preserves entered feedback, prevents duplicates, and provides a clear retry path.
- The planned release commit and annotated tag have not yet been created.

#### 1.2.5.3 Known discrepancies

- The form links to the Public Feedback Policy, which explains the public nature of submitted feedback, but does not display an equivalent warning immediately at the submission decision point.
- The deployed Prototype Status page materially understates the implemented feedback functionality documented by the Phase 1 record and current remote evidence.

#### 1.2.5.4 Required follow-up

- Conduct and document a non-sensitive, controlled failure observation, without creating a public issue.
- Update the Prototype Status page with a dated current-state summary based on the documentation-consistency comparison.
- Finalize the intended repository materials, commit them on `main`, and create and push the annotated tag specified in Table 1.
## 1.3 Release procedure and scope

### 1.3.1 Release procedure

1. Finalize this verification record locally and place it in `docs/verification/`.
2. Commit this record and any other materials intended for the release snapshot on `main`.
3. Create the annotated tag specified in the **Annotated tag** row of Table 1 on that commit.
4. Push `main` and the annotated tag to GitHub.
5. Confirm in GitHub that the tag resolves to the intended commit and that the corresponding deployment evidence remains available.

No release material should be edited after the tag is created. A later correction requires a new commit and a new annotated tag.
### 1.3.2 Scope limitation

This record establishes the remote ActionForge system state associated with the **Baseline commit**, as observed on the `Verification date`, together with the specified historical production evidence. It does not establish independent usability, accessibility across user groups, long-term reliability, governance adequacy, failure-recovery behaviour, or future deployment behaviour.

A later annotated tag may identify a release snapshot, but it does not retrospectively extend the evidence recorded here beyond the Baseline commit, the `Verification date`, and the stated historical evidence.
